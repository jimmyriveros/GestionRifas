# PROMPT FASE 0 — ARQUITECTURA Y PLANIFICACIÓN

Ejecuta únicamente la Fase 0 del proyecto definido en `CLAUDE.md`.

No implementes todavía las funcionalidades de la aplicación.

Puedes crear la estructura documental y los archivos de configuración mínimos necesarios, pero no debes construir páginas, formularios, autenticación, migraciones definitivas ni módulos funcionales.

## Objetivo

Transformar la especificación maestra en un plan técnico completo, consistente y ejecutable.

## Trabajo obligatorio

1. Inspecciona el repositorio actual.
2. Identifica si es un repositorio vacío o existente.
3. Lee todos los documentos disponibles.
4. Crea o actualiza:

   * `docs/MASTER_SPEC.md`
   * `docs/ARCHITECTURE.md`
   * `docs/DATA_MODEL.md`
   * `docs/BUSINESS_RULES.md`
   * `docs/SECURITY.md`
   * `docs/IMPLEMENTATION_PLAN.md`
   * `docs/DECISIONS.md`
   * `docs/PHASE_STATUS.md`
   * `docs/KNOWN_ISSUES.md`
   * `docs/TESTING.md`
5. Diseña el modelo de datos completo.
6. Define relaciones, cardinalidades y ownership.
7. Define la estrategia multiorganización.
8. Define la matriz de permisos para Owner, Admin y Seller.
9. Define las políticas RLS necesarias, sin implementarlas todavía.
10. Define las funciones transaccionales necesarias.
11. Define la estrategia para pagos y asignaciones.
12. Define el manejo de estados calculados.
13. Define la arquitectura de carpetas.
14. Define las rutas de Next.js.
15. Define componentes y módulos principales.
16. Define los límites de cada fase.
17. Identifica riesgos técnicos y de seguridad.
18. Identifica casos extremos.
19. Define criterios de aceptación verificables por fase.
20. Define estrategia de pruebas.
21. Define estrategia de seed.
22. Define estrategia de despliegue.

## Revisión lógica obligatoria

Comprueba especialmente:

* Precio predeterminado de `$100.000 COP`.
* Dinero almacenado como enteros.
* Números guardados como texto.
* Máximo cuatro dígitos.
* Conservación de ceros iniciales.
* Combinación única por rifa.
* Prohibición de duplicados entre vendedores.
* Snapshot de `sale_price`.
* Separación entre estado de inventario y estado de pago.
* Pagos distribuidos entre boletas.
* Atomicidad de pagos.
* Anulación sin eliminación física.
* RLS para vendedores.
* RLS entre organizaciones.
* Auditoría.

## Entregable especial

En `docs/IMPLEMENTATION_PLAN.md`, crea una sección por fase con:

* Objetivo.
* Dependencias.
* Entregables.
* Archivos esperados.
* Pruebas.
* Criterio de finalización.
* Elementos explícitamente fuera de alcance.

## Restricciones

* No implementes la Fase 1.
* No instales dependencias innecesarias.
* No construyas pantallas funcionales.
* No crees migraciones definitivas.
* No continúes automáticamente.

Al terminar, entrega el reporte obligatorio definido en `CLAUDE.md` y detente.

# PROMPT FASE 2 — BASE DE DATOS, RESTRICCIONES Y RLS

Ejecuta únicamente la Fase 2 del proyecto definido en `CLAUDE.md`.

La Fase 1 debe estar completada.

## Objetivo

Implementar el modelo de datos completo, las restricciones de integridad, las políticas RLS, las funciones de seguridad y los seeds de desarrollo.

No construyas todavía las interfaces completas del portal Owner o Seller.

## Implementación obligatoria

Crea migraciones versionadas para:

* `organizations`
* Perfiles y membresías.
* `raffles`
* `clients`
* `tickets`
* `payments`
* `payment_allocations`
* `audit_logs`

Agrega:

* UUID.
* Foreign keys.
* Restricciones `NOT NULL`.
* Restricciones `CHECK`.
* Restricciones únicas.
* Índices.
* Timestamps.
* Soft delete o archivado cuando corresponda.

## Reglas obligatorias de tickets

Implementa:

* `daily_number` como texto.
* `weekly_number` como texto.
* Validación de uno a cuatro dígitos.
* Conservación de ceros iniciales.
* Combinación única por organización y rifa.
* Duplicados bloqueados incluso entre vendedores.
* Combinaciones anuladas no reutilizables en el MVP.
* Estados de inventario válidos.
* Precio de venta como entero.
* `sale_price` inmutable después de existir pagos, salvo procedimiento administrativo documentado.

## Reglas obligatorias de pagos

Implementa:

* Montos enteros positivos.
* Relación entre pagos y asignaciones.
* Imposibilidad de asignar pago a una boleta de otro cliente.
* Imposibilidad de asignar pago a una boleta de otro vendedor sin autorización.
* Imposibilidad de sobrepagar.
* Historial de anulaciones.
* Integridad referencial.

Crea el diseño y, cuando corresponda a esta fase, las funciones SQL/RPC necesarias para operaciones atómicas.

La interfaz de pagos se construirá en la Fase 5.

## RLS obligatorio

Implementa y prueba políticas para:

### Owner y Admin

* Acceso autorizado a los datos de su organización.
* Sin acceso a otras organizaciones.

### Seller

* Solo sus clientes.
* Solo sus boletas.
* Solo sus pagos.
* Solo sus asignaciones.
* Solo sus métricas derivadas.
* Sin acceso a otros vendedores.

Protege también:

* Inserts.
* Updates.
* Deletes.
* RPC.
* Funciones con `security definer`.

Configura correctamente `search_path` en funciones privilegiadas.

## Auditoría

Implementa la infraestructura base para registrar cambios críticos.

Evita ciclos, recursión infinita o políticas RLS que bloqueen los triggers.

## Seed

Crea datos de desarrollo con:

* Una organización.
* Un Owner.
* Un Admin.
* Dos vendedores.
* Una rifa activa de `$100.000 COP`.
* Clientes.
* Boletas disponibles.
* Boletas asignadas.
* Pagos parciales.
* Pagos completos.

No incluyas secretos reales.

## Pruebas obligatorias

Prueba directamente la base de datos:

1. Duplicado en la misma rifa.
2. Duplicado entre vendedores.
3. Misma combinación en otra rifa.
4. Más de cuatro dígitos.
5. Caracteres no numéricos.
6. Ceros iniciales.
7. Aislamiento entre organizaciones.
8. Seller consultando otro Seller.
9. Seller modificando otro Seller.
10. Sobrepago.
11. Pago para boleta de otro cliente.
12. Restricciones de estados.
13. Migración limpia desde cero.
14. Seed limpio.
15. Rollback o estrategia de recuperación documentada.

## Restricciones

* No construyas todavía el portal Owner completo.
* No construyas todavía el portal Seller completo.
* No construyas la interfaz completa de pagos.
* No continúes con la Fase 3.

Actualiza la documentación.

Entrega el reporte obligatorio y detente.

# PROMPT FASE 4 — PORTAL SELLER Y CLIENTES

## Gestión de boletas

* Tabla de boletas propias.
* Búsqueda por número diario.
* Búsqueda por número semanal.
* Búsqueda por código.

## Creación por vendedor

Cuando la rifa lo permita:

* Crear una o varias boletas.
* Validar los números.
* Bloquear duplicados.
* Dejar en `pending_approval`.
* Mostrar estado y explicación.

Cuando no esté permitido:

* Ocultar o deshabilitar la acción.
* Explicar que el administrador debe asignar las boletas.

## Clientes

Implementa:

* Listado.
* Búsqueda.
* Filtros.
* Creación.
* Edición.
* Archivado.
* Vista detallada.

Campos:

* Nombre.
* Alias.
* Teléfono.
* Email.
* Notas.

## Perfil de cliente

Muestra:

* Información.
* Boletas.
* Fecha de compra.
* Número diario.
* Número semanal.
* Precio.
* Estado de inventario.
* Estado de pago disponible hasta esta fase.
* Total comprado.
* Historial disponible.

La información financiera completa se conectará en la Fase 5.

## Asignación

Permite:

* Seleccionar un cliente existente.
* Crear un cliente desde el flujo.
* Asignar una boleta.
* Asignar varias boletas cuando sea seguro.
* Registrar `sale_date`.
* Copiar `sale_price`.
* Cambiar estado a `assigned`.

Bloquea:

* Boletas incompletas.
* Pendientes.
* Anuladas.
* De otro vendedor.
* De otra organización.
* Combinaciones inconsistentes.

## Seguridad

Prueba que el Seller no pueda:

* Ver clientes de otro Seller.
* Consultar boletas de otro Seller.
* Asignarse boletas ajenas.
* Modificar IDs para acceder a otros registros.
* Crear boletas cuando la rifa no lo permite.
